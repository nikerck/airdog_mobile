# 待办同步机制

一句话：**服务端是权威，手机上的 SQLite（drift）只是缓存**。写操作先打接口，成功后才更新本地；
读操作永远只读本地，靠后台拉取把服务端的变化灌进来。

## 一、三条链路

```
      ①写：先请示服务端
┌─────────────┐   POST/PATCH/DELETE   ┌──────────────┐
│  你点保存   │ ────────────────────► │   服务端      │
└──────┬──────┘                       └──────┬───────┘
       │ ②用返回的完整对象                 │
       ▼                                  │
┌─────────────┐                            │
│  本地 drift  │ ◄──────────────────────────┘
└──────┬──────┘   ③拉：/api/sync/changes?since=游标
       │         （冷启动一次 + 前台每 30 秒）
       ▼
   页面自动刷新（Stream 订阅）
```

### ① 拉（pull）

```dart
GET /api/sync/changes?since=1761290000000&limit=500
```

返回 `updatedAt > since` 的所有行，**包括已删除的**（`deletedAt` 有值），客户端：

1. 按 `id` 做 `insertOnConflictUpdate`（有就覆盖，没有就插）
2. 墓碑行写入 `deleted_at`，界面自然就看不到它了
3. 游标 = `hasMore ? nextSince : serverTime`，存进 `SharedPreferences` 的 `sync.since`
4. `hasMore=true` 就接着拉，最多 20 页

**为什么要墓碑**：如果服务端直接不返回删掉的行，客户端就不知道「这条没了」，
只能靠全量对比，效率极低。

### ② 写（write-through）

| 操作 | 请求 | 本地动作 |
|---|---|---|
| 新建 | `POST /api/todos` | 用返回对象 upsert |
| 编辑 | `PATCH /api/todos/{id}` + `rev` | 同上 |
| 勾完成 | `PATCH {doneAt, doneBy}` | 同上 |
| 删除 | `DELETE /api/todos/{id}` | 软删（置 `deletedAt`，`rev+1`） |

规则：**接口失败就保持本地原样**，页面弹提示。宁可让用户重试，也不做「本地先改、
后台失败就悄悄丢掉」的假同步。

例外：删除时如果服务端返回 404（别的设备已经删了），本地照样删掉 —— 否则这条会永远卡住。

### ③ 图片

图片不进 JSON：

```
选图 → 存本地 → POST /api/files 拿 fileId → 待办只存 fileId 数组
拉取时：fileId → 查 file_cache → 没有就下载 → 存回缓存
```

服务端按 sha256 去重，同一张图传两次不会存两份。

## 二、什么时候同步

| 时机 | 触发点 | 失败表现 |
|---|---|---|
| 冷启动 / 登录后 | `startupSyncProvider` | 弹「同步失败」 |
| **前台每 30 秒** | `SyncPoller`（`sync_poller.dart`） | 静默，只记日志 |
| 回到前台 | 生命周期 `resumed` → 立刻拉一次 | 静默 |
| 写冲突（409） | `_guardConflict` 补拉一次 | 提示「数据已被更新」 |
| 成员 / 头像变化 | 每轮轮询后 `spacesProvider.refresh()` | 静默，内容没变不重建 |

**成员和头像**走另一条路：`GET /api/spaces`（不在 `sync/changes` 里）。
轮询每轮结束后顺手刷一次，比对内容没变就不更新状态——
所以对方改头像/昵称，最多 30 秒就能在这边看到，而界面不会每 30 秒白重建一次。

轮询的细节：

- **只在前台跑**，切后台立刻停（省电省流量）
- **不重叠**：上一轮还没回来就跳过这一轮；`pullAll()` 内部也会合并并发调用
- **回到前台立刻拉**，不用等下一个 30 秒
- 退出登录时 `ShellPage` 销毁 → `poller.stop()`

## 三、冲突怎么办

用 `rev` 做乐观锁：

```json
PATCH /api/todos/{id}   { "title": "新标题", "rev": 3 }
```

- `rev` 与服务端一致 → 成功，`rev` 变 4
- 不一致（别人先改了）→ `409 / 2003`
- 客户端收到后：先 `pullAll()` 把服务端最新数据拉下来，再提示「数据已被更新，已为你刷新」

策略是**后写覆盖**，不做字段级合并。两个人同时改同一条，后点保存的那个赢。

## 四、常见疑问

**Q：手机上杀掉 App 再打开，数据会丢吗？**
不会。本地 SQLite 有完整副本，先显示缓存，再后台补增量。

**Q：为什么对方改了，我要等 30 秒？**
就是为了省电。想立刻看到可以切到后台再切回来（会立刻拉一次）。
觉得 30 秒太慢，改 `SyncPoller(interval: ...)` 一处即可。

**Q：断网时能新建待办吗？**
**不能**。没有离线队列，写操作会直接失败并提示。这是已知缺口，见下。

**Q：游标存在哪？**
`SharedPreferences` 的 `sync.since`。如果本地库被清空但游标还在（重装、快照回滚），
`pullAll()` 会检测到「本地三张表都空」并退回全量拉取。

**Q：为什么 `updatedAt` 由服务端生成？**
手机时钟不可信（可能被手动改、时区乱），用客户端时间会漏数据或重复拉。

## 五、目前没有做的

| 缺口 | 影响 | 备注 |
|---|---|---|
| 离线队列 | 断网写入直接失败 | 需要 `pending` 标记 + 补传 |
| 实时推送 | 只能靠轮询 | 可换 SSE/WebSocket |
| 字段级合并 | 同时编辑会整条覆盖 | 目前够用 |
| 图片懒加载 | 首次拉大量带图待办会慢 | 可先落文字、图片后台补 |
| 相册说明 | 只能看不能改 | 服务端缺 `PATCH /api/photos/{id}` |
